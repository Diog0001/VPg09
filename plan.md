# План работ — Вязь

Связанные документы: [PROMPT.md](./PROMPT.md) · [architecture.md](./architecture.md) · [TZ.md](./TZ.md) · [README.md](./README.md)

Принцип: **каждый срез можно кликнуть руками**. Нет фазы «сначала инфраструктура 3 недели».

Оценка дана для одного vibe-кодера в Cursor. Календарь — ориентир, важнее порядок.

---

## Обзор фаз

```text
0  Каркас и доменные типы          2–3 дня
1  Доска + превью задачи           3–4 дня
2  Конструктор: mindmap и рёбра    5–7 дней     ← сердце продукта
3  Три слоя путей + key-инварианты 3–4 дня
4  История и эволюция              2–3 дня
5  AI descriptive + chat           4–5 дней     ← MVP
6  AI linker (рекомендации)        3–4 дня
7  Конфиг пространства             3–4 дня
8  Контекст: файлы + GitHub        5–7 дней
9  Агенты                          5–7 дней
10 Совместная работа и полировка   по необходимости
```

MVP продукта = конец фазы 5.  
Полная постановка промпта ≈ конец фазы 9.

## Фаза 0 — Каркас

**Цель:** пустой, но правильный репозиторий.

Работы:

- Монорепо: `apps/api` (FastAPI) + `apps/web` (Vite + React + `@carbon/react`).
- Docker Compose: Postgres 16.
- API: SQLAlchemy 2 + Alembic, модели User, Workspace, Membership, Task, TaskType, Edge, Event.
- Enums: `TaskStatus`, `RelationKind`, `RelationType`, `TaskEditor`.
- Сиды: built-in типы `task`, `note`, `sketch`, `design`; один пользователь, один workspace, 5 задач разных типов без рёбер.
- Web: IBM Plex, токены из `carbon-design-design.md`, пустой layout Carbon (Header + Content).
- Генерация TS-клиента из OpenAPI.
- `.env.example`, скрипты `dev` / `db:up` / `db:migrate`.

DoD:

- `docker compose up` поднимает БД.
- `uvicorn` отдаёт `/health` и `/docs`.
- Vite открывает белый Carbon-шелл (Plex, Blue 60).
- Миграции проходят; в БД можно создать две задачи и ребро SQL-ом.

Не делать: auth-провайдеры сверх одного метода, CI в Kubernetes.

## Фаза 1 — Доска

**Цель:** выглядит как таск-трекер.

Работы:

- Список workspace / создание.
- Канбан по `status`.
- Создание задачи с доски с выбором типа (дефолт `task`).
- Карточка показывает иконку/цвет TaskType.
- Drag-and-drop смена статуса.
- Карточка: title, priority, due date.
- Клик по карточке → **превью** (`/w/:workspaceId/tasks/:taskId`): поля, описание, статус, пустой список связей.
- Из превью можно вернуться на доску. Кнопки конструктора на этой фазе ещё нет (или disabled).
- Простая страница входа (credentials или magic, что быстрее и локально).

DoD:

- Сценарий «создал 5 задач разных типов, растащил по колонкам, открыл превью, закрыл» работает без перезагрузки вручную.
- Клик по карточке **не** открывает mindmap.

---

## Фаза 2 — Конструктор (mindmap)

**Цель:** из превью можно войти в конструктор; все ветки — задачи.

Работы:

- Кнопка «Открыть конструктор» в превью → `/w/:workspaceId/tasks/:taskId/map`.
- Холст `@xyflow/react`, центр — текущая задача.
- Автоукладка первого открытия: ELK (radial вокруг фокуса). Дальше — ручной drag в ViewState.
- Подгрузка соседей радиуса 1, затем 2.
- Создание ветки с холста = выбор TaskType + новая **задача** + ребро.
- Создание ребра drag-to-connect к уже существующей задаче.
- Выбор type при создании связи (kind пишется в БД: дефолт `primary/next`).
- Клик по ветке открывает превью этой задачи, не сразу её холст.
- Навигация: «к превью», «на доску».

DoD:

- Критерий 3 из ТЗ без key-предупреждений ещё допустим, но связи создаются визуально и являются задачами.
- Неограниченная вложенность: цепочка из 6 задач открывается с любой середины через превью → конструктор.

## Фаза 3 — Три пути

**Цель:** основной / второстепенный / ключевой — не подписи, а поведение.

Работы:

- Тумблеры слоёв на холсте.
- Стили рёбер по kind.
- Форма связи: сначала kind, потом type из реестра этого kind.
- Cycle detection для primary и key, понятная ошибка.
- Key-closure API.
- Диалог удаления: список зависимых по key.
- Badge на карточке доски: «есть key» / «есть контекст».

DoD:

- Нельзя сохранить цикл primary/key.
- Удаление источника key не проходит без явного подтверждения.
- Фильтр «только основной путь» прячет косвенные задачи.

Тесты:

- unit на cycle detection;
- unit на key-closure;
- integration: создать 3 kind и получить focus с фильтрами.

## Фаза 4 — Эволюция

**Цель:** работа внутри таска оставляет след.

Работы:

- Запись Event на create/update/delete node/edge.
- Timeline в превью.
- Undo последнего действия пользователя (команда + стек в рамках сессии и/или replay события).
- Версия задачи + отображение «изменено когда».

DoD:

- Связал, переименовал, отменил — граф вернулся.
- Timeline показывает автора (user).

## Фаза 5 — ИИ: описание и чат  ← MVP

**Цель:** нейронка бустит смысловой слой.

Работы:

- Абстракция провайдера (OpenAI-compatible).
- Сборка ContextBundle из focus graph (пока без файлов).
- Summarize task / subgraph.
- Чат в превью и в конструкторе, стриминг.
- Инструменты: `get_focus_graph`, `search_tasks`.
- Системный промпт: не выдумывать узлы, цитировать title.

DoD:

- Сценарии 1–7 из ТЗ зелёные.
- Без ключа провайдера UI честно говорит «ИИ выключен», граф работает.

---

## Фаза 6 — ИИ: рекомендации связей

**Цель:** рекомендательная модель.

Работы:

- Linker: кандидаты рёбер по эмбеддингам title+body (если pgvector ещё нет — LLM-only по focus + случайной выборке задач workspace с лимитом).
- Сущность Suggestion: pending/accepted/rejected.
- UI: список предложений, accept создаёт ребро, reject логируется.
- Запрет auto-accept для `key`.

DoD:

- На графе из 15+ узлов есть хотя бы несколько осмысленных предложений.
- Reject не создаёт ребро.

## Фаза 7 — Конфиг

**Цель:** пространство настраивается.

Работы:

- GlobalConfig + WorkspaceConfig в БД.
- Страница настроек пространства: колонки доски, поля карточки, включённые relation types, типы задач, модель ИИ.
- Хранение ключа провайдера encrypted / только env на MVP, если encryption ещё рано — явно задокументировать долг.
- Реестр кастомных `RelationType` с обязательным kind.
- CRUD своих `TaskType`: slug, label, icon, editor, видимость полей. Нельзя удалить built-in.

DoD:

- Смена колонок доски не требует деплоя.
- Выключенный relation type нельзя выбрать на холсте.
- Можно завести тип `bug` и создать им ветку. Выключенный `sketch` не предлагается при создании.

## Фаза 8 — Контекст продукта

**Цель:** ИИ видит продукт, а не только карточки.

Работы:

- Upload markdown/txt/pdf → chunks.
- GitHub source: token, выбор репо, sync README + issues (PRs если успеется).
- Показ источников в настройках, lastSyncedAt.
- Чанки попадают в ContextBundle чата.
- Цитирование источника в ответе.

DoD:

- Пункт 8 приёмки ТЗ.
- Отключение источника убирает его из промпта.

Риск: rate limit GitHub. Митигация: ручной sync, кэш, не поллер каждую минуту.

## Фаза 9 — Агенты

**Цель:** не один чат, а роли в пространстве.

Работы:

- AgentConfig: role, prompt, provider, trigger = manual на старте.
- Роли: summarizer (уже есть), linker (уже есть), planner (черновик подграфа), reviewer (пробелы, разрывы key).
- AgentRun log.
- UI: список агентов, «запустить на этом узле».
- Draft-задачи от planner — пачка suggestions, не сразу 20 живых карточек.

DoD:

- В настройках пространства можно включить planner, запустить на эпике, принять часть черновика.
- Каждое действие агента в Event/AgentRun.

Не делать on_event-триггеры, пока manual не стабилен.

## Фаза 10 — Полировка

Только после живого использования фаз 5–8.

- Виртуализация доски.

- Комментарии.
- Realtime.
- Sketch-редактор вместо заглушки.
- Экспорт GraphML/Mermaid.
- Тёмная тема, онбординг «три пути».

## Порядок в Cursor

На каждую фазу один чат/ветка:

1. Прочитать `PROMPT.md` + инварианты.
2. Прочитать соответствующий кусок архитектуры и ТЗ.
3. Реализовать только тикеты фазы.
4. Прогнать DoD руками.
5. Обновить «статус фазы» в README.

Запрещённые просьбы агенту до фазы 5: «добавь Kafka», «сделай микросервисы», «нарисуй PixiJS на 10k узлов».

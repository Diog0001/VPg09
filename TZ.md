# Техническое задание — Вязь

Связанные документы: [PROMPT.md](./PROMPT.md) · [architecture.md](./architecture.md) · [plan.md](./plan.md) · [README.md](./README.md)

---

## 1. Цель

Создать платформу управления работой над продуктом, в которой:

- данные — **граф задач**, а не дерево;
- первое, что видит человек — **доска**;
- открытие задачи — **превью**; в mindmap-конструктор вход отдельным действием;
- все ветвления — тоже задачи; у задачи есть **тип** (`task`, `note`, `sketch`, `design` или свой); различается тип карточки и слой связи;
- ИИ и агенты работают от **контекста продукта** (граф + GitHub + документы);
- классический трекер не выкинут: статусы, сроки, исполнители, доски, карточки.

Вязь должна сделать смысловую работу (проектирование, зависимости идей, эволюция частей) таким же первоклассным действием, как «перетащить карточку в Done».

---

## 2. Цели и не-цели

### Делаем

- Граф задач и типизированных рёбер.
- Каталог типов задач: дефолтные + пользовательские.
- Три слоя путей: основной, второстепенный, ключевой — все вершины задачи.
- Доска + превью задачи + конструктор (mindmap).
- Конфиг пространства: провайдеры, агенты, форматы.
- Глобальный конфиг с наследованием в продукт.
- Подключение GitHub (чтение) и загрузка документов.
- Рекомендации и описания от ИИ по подграфу и контексту.
- Журнал изменений узла и рёбер, undo.

### Не делаем в первой версии

- Мобильные приложения.
- Маркетплейс агентов.
- Offline-CRDT и одновременное редактирование холста многими курсорами.
- Импорт всей Jira/Linear как миграционный комбайн.
- Автономные агенты, которые без подтверждения переписывают граф.
- Шардинг, Kubernetes, отдельная event-шина.

## 3. Аудитория

| Персона | Зачем Вязь |
|---|---|
| Соло-основатель / vibe-кодер | Держать продукт как смысловую карту задач, а не как свалку тикетов |
| Малая команда 2–8 человек | Видеть, как задачи связаны по смыслу, не только по статусу |
| Исследователь / дизайнер | Заметки, скетчи и дизайн — задачи своих типов в том же графе |

Первый пользователь системы — автор этого репозитория. ТЗ пишется так, чтобы продукт можно было собрать итерациями в Cursor.

## 4. Пользовательские сценарии

### 4.1. Пространство

- Создаю workspace «мой продукт».
- Задаю название, описание, формат доски (колонки).
- (Позже) подключаю AI-провайдера и GitHub.

### 4.2. Классический трекер

- Создаю задачу с доски (тип по умолчанию `task`, можно выбрать другой).
- Меняю статус drag-and-drop.
- Ставлю срок, приоритет, исполнителя.
- Вижу список/канбан как в обычном трекере.

### 4.3. Превью задачи

- Кликнул карточку на доске — открылось превью, не холст.
- В превью вижу тип задачи, описание, статус (если тип его показывает), срок, исполнителя, вложения.
- Вижу связанные задачи, сгруппированные по слоям: основной / второстепенный / ключевой.
- Могу править поля, не заходя в конструктор.
- Отдельной кнопкой вхожу в конструктор.

### 4.4. Mindmap-конструктор

- Из превью открываю холст с этой задачей в центре.
- Создаю ветку — выбираю тип (`task` / `note` / `sketch` / `design` / свой) и получаю **новую задачу** + ребро.
- Соединяю уже существующие задачи ребром, выбираю слой.
- Фильтрую холст по слою.
- Строю основной путь от большого контекста к следующему большому (цепочка задач).
- Вешаю косвенный контекст — задача на `secondary`, часто типа `note` или `sketch`.
- Помечаю ключевую связь: «эта задача не имеет смысла без той».
- Клик по ветке открывает превью той задачи (или делает её центром после явного действия).
- Система не даёт тихо удалить задачу, от которой зависят key-задачи.

### 4.5. Эволюция

- Открываю историю задачи: что менялось, кто связал, какой агент предложил ребро.
- Откатываю последнее изменение.
- Вижу, как подграф задачи вырос за неделю.

### 4.6. ИИ

- Прошу резюме задачи и её окрестности.
- Получаю предложения связей (не записанные автоматически).
- Спрашиваю: «что блокирует эту задачу?» / «какой основной путь к релизу?».
- Запускаю планировщик: декомпозиция эпика в черновик подграфа задач, который я подтверждаю.

### 4.7. Контекст продукта

- Подключаю репозиторий GitHub.
- Загружаю PDF/Markdown с описанием продукта.
- ИИ использует эти источники, отвечая про конкретный продукт, а не «вообще».

### 4.8. Конфиг

- На глобальном уровне задаю доступные провайдеры, дефолтные типы связей и типы задач.
- В пространстве включаю нужных агентов, меняю формат карточки, добавляю свой `RelationType` с обязательным kind и свой `TaskType` (slug, иконка, редактор).

## 5. Функциональные требования

### F1. Учётные записи и пространства

- Регистрация/логин.
- CRUD workspace.
- Роли: owner, admin, member, viewer.
- На MVP достаточно одного пользователя на workspace, но модель ролей закладывается сразу.

### F2. Задачи и типы задач

- Вершина графа всегда `Task`.
- У задачи обязателен `typeId` → `TaskType`.
- Дефолтный каталог: `task`, `note`, `sketch`, `design`. Удалить built-in нельзя, выключить можно все кроме `task`.
- Пользовательские типы: CRUD в глобальном конфиге и в конфиге пространства (slug, label, icon, color, editor, видимость полей трекера, extra fields).
- Поля трекера: title, body, status, priority, assignee, due date — видимость зависит от типа.
- Вложения принадлежат задаче. Для `sketch`/`design` редактор холста — часть превью (на MVP допустим markdown + файлы).
- Создание ветки = выбор типа + создание задачи + ребра.
- Soft delete. Задачи пользовательского типа остаются, если тип выключили (тип помечается archived, карточки читаются).
- Кастомные поля — из CardFormat и extraFields типа.

### F3. Рёбра

- Создание, удаление, смена type/kind как явное действие.
- Обязателен `RelationKind`.
- Валидация циклов для `primary` и `key`.
- Запрет дубля одинаковой тройки (source, target, type+kind).
- Неограниченное число рёбер у задачи.

### F4. Представления

- Board: колонки по статусу, drag-and-drop. Клик открывает превью.
- Preview: полная карточка задачи, связи по трём слоям, история, AI, кнопка «Открыть конструктор».
- Constructor (focus mindmap): радиус 1–2, zoom/pan, ветки = задачи своего типа.
- Из конструктора: «к превью» и «на доску».

### F5. Ключевой путь

- Визуально отличим (цвет/толщина/иконка).
- Операции удаления/архива показывают затронутые задачи.
- Запрос key-closure.

### F6. История

- Любая мутация → событие.
- Просмотр timeline задачи.
- Undo последнего локального действия пользователя.

### F7. ИИ (после ядра графа)

- Один провайдер через OpenAI-compatible API.
- Summarizer: задача + focus graph.
- Linker: предложения рёбер с confidence и kind.
- Чат с инструментами чтения графа.
- Accept / reject suggestions.
- Запрет автозаписи `key` рёбер.

### F8. Контекст

- Загрузка `.md`, `.txt`, `.pdf`.
- GitHub: OAuth или personal token, read-only sync README/issues/PRs.
- Источники видны в конфиге пространства.
- Чанки используются в чате; на MVP достаточно naive chunking без идеального GraphRAG.

### F9. Конфиг

- Global defaults: типы связей, типы задач, форматы.
- Workspace overrides: провайдер, модель, агенты, колонки доски, видимые поля карточки, свой TaskType.
- Секреты не светятся в UI после сохранения.

### F10. Экспорт

- JSON: tasks, taskTypes, edges, kinds, relation types, events (опционально).
- Импорт того же формата без потери рёбер.

## 6. Правила трёх путей (нормативные)

Эти правила — часть ТЗ, не «дизайн на потом».

1. **Основной путь (`primary`)** соединяет главные задачи продукта. Это «о чём мы вообще делаем работу». Колонки доски не заменяют основной путь.
2. **Второстепенный путь (`secondary`)** присоединяет косвенные **задачи**: ресёрч, сопутствующая работа, дубли, противоречия. Он не двигает статус автоматически.
3. **Ключевой путь (`key`)** означает: целевая задача **не может существовать автономно** без источника. Это сильнее, чем «заблокировано» и сильнее, чем «подзадача».
4. Одна и та же задача может участвовать во всех трёх слоях одновременно.
5. UI обязан уметь показать слои раздельно и вместе.
6. На любом пути вершины — задачи. `note` / `sketch` / `design` — типы задач, не отдельные классы сущностей.

Примеры:

- «Релиз 1.0» `primary/next` «Онбординг» `primary/next` «Оплата» — основной путь продукта.
- «Онбординг» `secondary/supports` задачу типа `note` «Исследовать экраны конкурентов».
- «Онбординг» `secondary/supports` задачу типа `design` «Макет первого экрана».
- «Чек оплаты» `key/derives_from` «Модель биллинга» — без модели биллинга задача бессмысленна.

## 7. Требования к ИИ

ИИ решает две работы из промпта:

1. **Описательная модель** — объяснить узел, подграф, изменения, «что это и зачем».
2. **Рекомендательная модель** — предложить связи, декомпозицию, пробелы, риск разрыва key-пути.

Качество на MVP:

- Резюме не выдумывает задачи, которых нет в переданном графе.
- Предложение ребра всегда содержит `kind`, `type`, короткое «почему», confidence.
- Ответ чата цитирует задачи (`id`/`title`) и, если использовал документ, имя источника.
- Если контекста мало — модель говорит об этом, а не галлюцинирует GitHub.

## 9. Состав MVP

MVP считается достигнутым, когда выполняется сценарий приёмки ниже — **без** GitHub и без мультиагентной платформы.

**Входит:**

- Auth (минимальный).
- Workspace.
- Board.
- Превью задачи.
- Вершины только Task; дефолтные типы `task`, `note`, `sketch`, `design`; ветка = новая задача выбранного типа.
- Edges + три kind + базовые types.
- Конструктор (focus mindmap).
- История в превью.
- Один AI-провайдер: summary + chat по графу.
- Linker-suggestions (можно упрощённо).

**Сразу после MVP (фаза Context):**

- GitHub read-only.
- Загрузка документов.
- Форматы карточек/досок в конфиге, а не в константах.
- Пользовательские TaskType.

**Позже:**

- Полноценный canvas-редактор для типов `sketch` и `design`.
- Агенты PLANNER/REVIEWER с триггерами.
- Realtime collaboration.

## 10. Критерии приёмки

Сквозной сценарий:

1. Пользователь регистрируется и создаёт workspace «Вязь».
2. На доске создаёт задачи разных типов (`task`, `note`, `design`). Клик по карточке открывает превью, не холст.
3. Из превью «Ядро графа» входит в конструктор и:
   - строит основной путь из 4 задач;
   - создаёт косвенную задачу типа `note` и задачу типа `sketch` второстепенными рёбрами;
   - ставит 1 ключевую связь.
4. Пытается удалить источник key-связи — видит предупреждение и список зависимых задач.
5. Перетаскивает карточку на доске в In progress — статус совпадает в превью и в конструкторе.
6. Просит ИИ резюме фокус-графа — ответ опирается на существующие задачи.
7. Экспортирует JSON и видит все 3 kind.

Дополнительно для фазы Context:

8. Подключён README репозитория, чат отвечает с опорой на него.

## 11. Метрики продукта (ориентиры)

Не для первой учебной недели, но чтобы не строить «доску ради доски»:

- Время до первого ребра < 3 минут после создания workspace.
- Доля задач с хотя бы одним ребром > 60% к концу первой недели использования.
- Доля `secondary` рёбер > 20% — иначе снова получился Todo-лист.
- Хотя бы одно `key` ребро на пространство — иначе потерян инвариант промпта.
- Доля принятых AI-suggestions (когда появится линкер) — смотрим, не оптимизируем вслепую.
